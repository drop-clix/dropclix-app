# FIRE: Magic Link PKCE Auth Failure
**Date:** June 16, 2026
**Severity:** HIGH
**Status:** RESOLVED

## What Happened

Admin sent magic link invites to new clients via `signInWithOtp`. The flow: browser calls
`signInWithOtp` → Supabase emails a link pointing to `/auth/callback?code=xxx` → client
clicks link → PKCE code exchange should run and establish a session.

Instead, clients landed on `/login?error=auth_failed` with no way to sign in. The PKCE
verifier generated by `createBrowserClient` was stored in **localStorage** of the browser
where the link was _requested_. When the client opened the email in their default browser
(a different browser/device), no verifier existed → `exchangeCodeForSession` failed → redirect
to error. Also observed: first click on the link stalled while the exchange failed; a second
click on the same (now-expired) link redirected to `/login` with no error, because Supabase
had already consumed the code on the first attempt.

## Root Cause

PKCE verifier stored in browser localStorage. Clicking the magic link in a different
browser than where it was requested means no verifier exists → code exchange fails.
Also: first click stalls while exchange completes, second click succeeds because
session is already established.

Secondary cause: `proxy.ts` was calling `supabase.auth.getUser()` before the `/auth/`
passthrough check, which could interfere with the PKCE `?code=` query param on the
callback URL.

## What Was Done

1. Added `/auth/callback` `route.ts` (server-side) — failed (server has no localStorage access, can't find PKCE verifier)
2. Changed `emailRedirectTo` to `/auth/callback` — partial (still server-side; also fixed proxy ordering)
3. Moved `/auth/` passthrough before `getUser()` in proxy — helped (code param reaches handler intact)
4. Converted `/auth/callback` to client-side `page.tsx` — worked but only in same browser

## Why We Moved To Passwords

- PKCE magic links require same browser session
- Clients open email links in default browser which may differ from where they requested
- Too fragile for client onboarding
- Passwords work from any browser, any device

## Prevention

- Use password-based auth for client onboarding
- Magic link / forgot password as fallback only
- Never use PKCE magic links as primary client auth method
- Document in CLAUDE.md: `signInWithOtp` uses PKCE by default, requires same browser localStorage

## Resolution

[x] COMPLETE — password-based invite flow implemented in S50.

`createNewClient` now calls `adm.auth.admin.createUser({ email_confirm: true, user_metadata: { must_change_password: true } })`.
Admin copies temp credentials from modal and shares directly with client.
Client logs in with temp password → `layout.tsx` detects `must_change_password` flag → redirect to `/auth/set-password`.
Set-password page clears the flag and sends client to dashboard.
No email links involved in the happy path.
